Build a Module

Every Add/Edit/Delete screen in NeoEHS — Company today, Department or whatever comes next tomorrow — is built from the same five reusable pieces. This is the map of how they fit together, and the flow each one follows.

01

Five pieces, reused by every module

A module's List page and Form popup are the only code you actually write per module. Both pull from the same four shared files — and those files are the only place that ever talks to the backend.

PieceFileWhat it does
Popup shellcomponents/ui/Modal/Modal.jsxOpen/close, title, body, footer, Esc & backdrop close — same dialog for Add and Edit.
Form buttonscomponents/ui/Button/SubmitButton.jsx, ResetButton.jsxSubmit (spinner + label swap while loading) and Reset, dropped into the popup footer.

02

Add, Edit and Delete follow the same shape

All three end the same way — refresh the list — and only differ in what happens before that. Edit adds a load step and excludes its own record from the uniqueness check; Delete skips validation entirely and asks for confirmation instead.

03

One validator, four input shapes

rules and fileRules are both just functions that take a value and return an error string — that's why a normal field, an Add More row, a single image and an Add More image all run through the exact same validateForm.

Defining the schema

// normal fields
department_name: [rules.required("Department name is required"), rules.maxLength(150)],

// single image field
logo: [
  fileRules.allowedExtensions(["jpg", "png"], "Only JPG/PNG allowed"),
  fileRules.maxSize(2, "Logo must be under 2MB")
],

// Add More rows, each with its own image
items: {
  array: true,
  minItems: 1,
  itemSchema: {
    name:  [rules.required("Item name is required")],
    image: [fileRules.allowedExtensions(["jpg", "png"]), fileRules.maxSize(2)]
  }
}
Unique · Add vs Edit

Uniqueness is one field in the check list: excludeId: isEdit ? record.id : null. It's checked live before submit and re-checked by the backend on save — the second check is what actually protects against two people saving at once.

Editing a file field

An already-uploaded file arrives as a stored URL string, not a File. fileRules treats a non-empty string as already valid — the user only needs to pick a new file if they're replacing it.

04

The popup is one component, two moods

Modal.jsx doesn't know about Add or Edit — it just renders whatever title and footer it's given. The mode logic lives entirely in the form component that wraps it. 

<Modal
  show={formModal.show}
  onClose={handleClose}
  title={t(isEdit ? "department_master.edit" : "department_master.add")}
  footer={<>
    <ResetButton onClick={handleReset} disabled={submitting} />
    <SubmitButton label={isEdit ? "Update" : "Submit"} loading={submitting} form="department-form" />
  </>}

05

Delete never deletes

Every module's delete is a soft delete. Nothing is ever removed from the database — a row is just marked inactive and hidden from normal queries.

ColumnBeforeAfter delete
status10
trash'NO''YES'

getX() / getXById() queries already filter WHERE trash = 'NO', so a deleted row just stops appearing — no list query needs to change. 

// frontend — one call handles confirm, request, and the alert
const handleDelete = async (row) => {
  const deleted = await confirmAndDelete({
    url: `/api/admin/departments/${row.id}`,
    confirmTitle: "Delete this department?",
    successTitle: "Department deleted successfully",
    errorTitle: "Unable to delete this department right now"
  });
  if (deleted) fetchDepartments();
};

// backend — reuse the same soft-delete helper Company uses
const { softDeleteRecord } = require("../../../helpers/softDeleteHelper");
const deleteDepartment = (id) => softDeleteRecord(DEPARTMENT_MAS, id);
06

One Axios instance, one env var

Every request — list, create, update, delete, unique check — goes through the same instance. Nothing in a component ever writes a hostname. 

// frontend/src/config/axios.js
import axios from "axios";

const api = axios.create({
  baseURL: import.meta.env.VITE_API_BASE_URL
});

export default api;
// anywhere that needs the API
import api from "../../../config/axios";

api.get("/api/admin/departments");
api.post("/api/admin/departments", payload, { headers });
Configuring the base URL

Local dev: frontend/.env (gitignored) sets VITE_API_BASE_URL=http://localhost:5000. Deploying to a server means changing that one value and running npm run build — Vite inlines env vars at build time, so no source file is touched. Restart the dev server after editing .env locally; Vite won't hot-reload it.

08

Building "Department" — the checklist

Everything below reuses one of the five pieces. Nothing here is written from scratch.

  1. Backend model & controller — copy companyModel.js / companyController.js shape; call isValueTaken, softDeleteRecord, getSequence the same way.
  2. Routes — add the same five endpoints (list, next-id, create, update, check-unique) plus DELETE, mirroring adminRoutes.js.
  3. DepartmentList.jsx — fetch via api, delete via confirmAndDelete, render <DepartmentFormModal>.
  4. DepartmentFormModal.jsx — wrap <Modal>, define VALIDATION_SCHEMA (§3), call validateFormAdvanced then api.post/api.put on submit.
  5. Translations — add a department_master namespace to all six locale files, same keys Company already has.
Known gap

File/image validation is ready (§3), but the backend has no multipart upload handling yet (no multer). A module with real image fields needs that added first — it doesn't exist for Company either.
